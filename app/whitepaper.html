01 / THE PROBLEM

Accountability should not require exposing private evidence.

Projects often release money before delivery can be checked independently. Public transparency can also expose sensitive beneficiary, operational, or personal information.

01

Funding moves early

Donors need a release process that follows verified progress, not just a promise or a status update.

02

Evidence is sensitive

Implementers need to prove work without publishing the files, identities, or operational details behind it.

03

Decisions need context

Reviewers should decide against one exact evidence revision, with a record of disputes and approvals.

02 / HOW IT WORKS

A clear path from work completed to capital released.

Emberline models each project as a sequence of milestones. Each milestone has an amount, an evidence revision, a reviewer policy, and a quorum.

01
Define

The owner creates a project, sets milestones, and chooses the approval quorum.

02
Commit

The implementer hashes a private evidence package locally. The file is not uploaded.

03
Review

Independent reviewers assess the same evidence revision and approve or reject it.

04
Resolve

A rejection freezes the milestone. A corrected revision preserves the earlier history.

05
Release

When approvals reach quorum and sequence checks pass, the eligible tranche can release.

06
Audit

Commitments, decisions, proof references, and release transactions remain inspectable.

CORE GUARANTEESFiles stay private.Reviews stay independent.Policy stays enforceable.History stays inspectable.Files are hashed locally. Decisions are bound to reviewer, project, milestone, revision, commitment, and outcome.
03 / ATTESTCOIN AND USC

A verified bridge between review and release policy.

Attestcoin connects the reviewer decision recorded on Ethereum Sepolia to a release policy enforced on Creditcoin Testnet through USC.

THE INTEGRATION PATH

One proof must match the complete project state.

The destination verifier asks Creditcoin's BlockProver precompile to verify the source receipt and its Merkle and continuity proof. It accepts only the expected ReviewRecorded event from the configured immutable registry.

The project contract then checks reviewer, project, milestone, evidence revision, evidence commitment, and decision. Invalid or replayed proofs, duplicate votes, disputes, and out-of-order releases remain blocked.
